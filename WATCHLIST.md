# Jamf Deployer: watchlist

What this app is waiting for from Apple, Jamf or Microsoft, or must recheck. Check each item when the vendor ships an update.

Bundled versions are pinned in `Vendor/fetch.sh`; recheck the component items below whenever a version there changes.

- **Demo catalog on jamfplatform 1.8's names (new catalog tag by mid-January 2027, a few weeks after app 1.3.0):** jamfplatform 1.8.0 renamed PreStage attributes and flattened `pro_policy`; the old names keep working with deprecation warnings until 2027-02-03 (PreStages) and 2027-02-15 (policies). Move mac-maintenance, mac-provisioning, filevault-key-management, rosetta and self-service-maintenance (policies: `scripts.scripts` → `script_assignments`, and so on, and drop `fix_disk_permissions = false`, deprecated in jamfplatform 1.10.0) and mac-prestages, enrollment, mobile-prestages and mobile-enrollment (PreStages), and bump `validate/main.tf` (still jamfplatform 1.6.0, jamfprotect 0.12.0). In the mobile PreStages `mdm_removable = false` becomes `prevent_unenrollment = true` (the meaning flips): check each one by hand. Publish the tag only after the app release: apps before 1.3.0 can't read the new names. Before an app release bundles the plugin that removes the old names, stored captured, cloned and adopted code needs the same rewrite.
- **Settings Jamf Pro 11.34 retired (jamfplatform 1.10.0 deprecations; the plugin won't remove them before 2027-02-15):** a policy's `maintenance.fix_disk_permissions`, and `sign_quickadd_package` and `developer_certificate` in the user-initiated enrollment settings. On Jamf Pro 11.34 and later the plugin refuses `fix_disk_permissions = true`, and `sign_quickadd_package = true` without a developer certificate, at plan time (`ErrorTranslation` says what to change). Since 1.3.1, capture, clone and adopt leave them out when off, and keep them with a note when on (`RetiredSettings`). Blocks captured, cloned or adopted before 1.3.1 still contain `fix_disk_permissions = false`, so their Previews show a deprecation warning until they're captured again. Decide what to do with that stored code before an app release bundles a plugin that removes these settings (rewrite it, ask for a new capture, or strip it when the workspace is generated). The demo catalog's `fix_disk_permissions = false` (11 policies in mac-maintenance, mac-provisioning and filevault-key-management) goes in the catalog move above.
- **Concurrent configuration profile creates (Jamf, jamfpro plugin):** concurrent creates draw 500s from Jamf (which creates them anyway), and the jamfpro plugin requires `-parallelism=1`. If both change, applies could run in parallel.
- **Create 500/504 but created (Jamf):** the Classic lookups must ask for JSON (`Accept`), or JTKit gets XML and finds nothing. Not live-verified again since that fix: recheck in a live run.
- **terraform-backend-git 0.1.12 (bundled):** keeps a PID file in `$TMPDIR`; a stale lock branch stops a fresh backend from reading state. If a newer version fixes these, the own TMPDIR, the leftover kill on launch and Force Unlock’s direct branch delete can be revisited.
- **jamformer 0.7.x (bundled; same in 0.6.x):** emits Terraform-style identity imports that fail under OpenTofu (the app normalizes them); a settings-only selection fails with "No resources to query" (retried with a helper type). Since 0.7.0 it downloads the newest Terraform on every run unless handed one with `-terraform-path`: the app always hands it its own, and refuses an export without it (unit-tested). It writes every setting of an object, deprecated ones included (a policy's whole `maintenance` object, so `fix_disk_permissions` too); 0.7.0's own code names none of the settings jamfplatform 1.10.0 deprecates.
- **New Setup Assistant panes in Check for Changes (revisit next release):** a pane new in jamfplatform 1.8 (`skip_setup_items.liquid_glass`, and `device_features_tour` on mobile PreStages) counts as unchanged in Check for Changes until the tenant's saved state has it, so a change to that one pane made in Jamf only shows after the next deploy. Renamed attributes aren't affected: a change made in Jamf changes their old names too.
- **jamfplatform PreStages (Jamf):** PreStages with `scope_serial_numbers = []` get a 500 on PUT; capture drops the attribute.
- **jamfpro plugin and missing privileges:** a missing read privilege makes the jamfpro plugin retry forever, so privilege probes are time-boxed.
- **jamfpro plugin can’t list objects:** the exported "Not in code" check relies on `terraform query` instead.
- **Security Cloud activation profiles (Jamf):** activation profiles can’t be imported (to remove one, the app seeds a state holding it and destroys).
- **Jamf-Concepts/terraform-jamf-reference and terraform-provider-jsctfprovider (Jamf):** terraform-jamf-reference (MIT reference modules for jamfpro and Security Cloud) is the source to capture or adapt future catalog blocks from (compliance such as DISA STIG, NIST 800-171, CMMC and iOS CIS; CrowdStrike, Defender, SentinelOne; Platform SSO; Workbrew), crediting it; its modules pin older jamfpro versions. terraform-provider-jsctfprovider is watched, not used: Security Cloud stays on jamfplatform with one Platform API integration.
