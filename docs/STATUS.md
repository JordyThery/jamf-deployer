# Jamf Deployer — status, limitations and uncertainties

As of 2026-11-02 (1.2.0, released 2026-11-02; its changes are listed in [CHANGELOG.md](../CHANGELOG.md)). The release check passed on 2026-11-02 against the published JTKit 1.3.2 in about 21 minutes. The open items, limits and what is live-verified, in one place.

## Never exercised live (schema-verified, validated, but unapplied)
- ADE `.p7m` / Apps and Books `.vpptoken` uploads and Protect registration in Day 0 — wired and spec-verified, needing real Apple/Protect artifacts to fire for the first time.
- Jamf Pro below 11.31 — no such tenant to test the degradation path.

## Known behavioral gaps
- **Adopt’s secret settings (1.2.0)** are unit-tested on a real jamformer export; adopting a Wi-Fi, VPN, SCEP or LDAP profile with a real secret isn’t live-verified yet.
- **terraform-backend-git 0.1.12 and stale locks:** while a lock branch is left behind (a canceled run), a backend process started fresh can’t read that state (“non-fast-forward update”), so even `init` fails, and the engine’s own `force-unlock` can’t run. The exported Force unlock workflow and the app’s **Force Unlock…** therefore delete the lock branch directly; the app also reports such a read failure as the teammate’s lock.
- **plan.sh** reads credentials with `security`, which macOS asks permission for the first time; automated tests can’t click that prompt, so its Keychain step is verified by hand. Team Mode workspaces get a `plan.sh` that explains why it can’t run there.
- **“Keep This Change”** adopts the drifted value into the block’s setting when the block declares a drift binding for that field; fields without a binding fall back to acknowledgment (a later deploy reverts them, and the UI says so).
- **Create-500-but-created quirk** (Jamf, seen on policies, profiles, patch titles and App Installer deployments, as 500 and 504): under parallel load Jamf sometimes reports a server error after creating the object. Deploys make one change at a time: with four, and still with two, in parallel Jamf answered several configuration profile creates with 500s on an EU tenant, while one at a time created 124 fleet objects cleanly in under a minute, repeatedly. After a deploy, each failed create is looked up by its planned name; objects Jamf did create — and that the state doesn’t already track — become import blocks, so the next preview adopts them instead of hitting a duplicate. Ambiguous duplicate names are left for review rather than guessed. The recovery itself is live-verified (recovered objects adopted, the rest created, no duplicates left in Jamf). The Classic API lookups (policies, configuration profiles, patch titles) ask for JSON; a unit test covers that against a fake Jamf that answers XML unless asked for JSON, but it isn’t live-verified again yet. Since 1.1.1, a name lookup before the deploy that finds nothing (Jamf answers 404) counts as “no object had the name”, so policies and configuration profiles are recovered again; unit-tested against a fake Jamf. On jamfplatform 1.7.2 the preview after a recovery adopts the object (1 adopt, 0 create): the plugin’s plan-time name check doesn’t refuse it. That step runs live in every release check (`recoveredImportStillPreviews`); the 500 itself can’t be caused on purpose.
- **Baseline updates are per-block for Git-tag catalog sources** (tenants pin tags; blocks can opt into newer tags individually). Local-folder sources are always “latest”, so updates there remain all-or-nothing.
- **CIS benchmark ODVs** use baseline-recommended values; per-rule overrides aren’t editable yet.
- **Adopt**: provenance-tagged objects are detected and excluded by default, but re-binding them to their blocks (after state loss) isn’t built; adopted root objects can’t be individually stop-managed yet; composite-identity imports would pass through unnormalized (none exist in today’s providers).
- **Object editor** handles primitive attributes only (honestly labeled in the UI).
- Day 0: branding icon/banner upload (multipart) and full onboarding config are assist-level; APNs expiry has no public API anywhere (manual date).
- Drift noise classification is a curated attribute list — new computed attributes would initially show as actionable.
- **Fleet rollouts** run one tenant at a time in up to three rings (production tenants start in ring 2) and need at least two tenants with something to deploy. Catalog-release mode lists Git catalog sources only. A deploy with failures ends the rollout; a tenant closed without deploying gets its previous selections and release pin back. Live-verified with a local two-tag catalog (Sandbox deployed v1.0.1, Demo skipped and stayed on v1.0.0).

## Jamf Protect and Security Cloud
- **Jamf Protect Baseline** and **Security Cloud** are live-verified on a test environment entitled for both (the export UI suite of 1.1): deploy, no changes afterwards, export and move, the repository’s checks finding no changes, destroy. Security Cloud ran both ways: with **UEM Connect: Use the existing connection** (the integration unchanged afterwards), and, on the same environment with its integration removed first, making the connection itself (EXPORT_UEM_CONNECT=create). Both errors are live-captured and translated: a second integration where one exists, and *Use the existing connection* where there is none.

## Jamf Pro API connections
- A tenant connects through the Jamf Platform API or the Jamf Pro API (community jamfpro plugin 0.42.0 by Deployment Theory), chosen in the Connect wizard and fixed per tenant. Jamf Pro API tenants sign in with an API client or a user account.
- Jamf Pro API tenants deploy building blocks through each block’s `jamfpro/` module, and adopt, check for changes, keep or restore, add custom objects, roll out, export snapshots and documentation, run Day 0 and hand over. Software Updates, CIS Level 1, Security Cloud and the App Store blocks need the Jamf Platform API, and so do capturing blocks and cloning. Moving to the Jamf Platform API is Hand Over Tenant…, connect again, Adopt.
- Engine runs (previews, checks, deploys) use one operation at a time (`-parallelism=1`), as the plugin requires; previews and checks of large baselines are slower than over the Jamf Platform API, which reads in parallel.
- Every demo catalog block plus the App Catalog was live-verified through both connections on both test instances (the catalog UI suite of 1.1): deploy, every object checked in Jamf, no changes afterwards, one change per object type detected (17 of 17), restore, removal checked in Jamf, tenant-wide settings restored. The same runs adopt six existing objects of different types (category, script, smart and static group, extension attribute, and a policy that uses them), confirm no changes, detect edits to the adopted policy and script, and restore them.
- Two jamfpro plugin quirks are handled in the modules: FileVault’s policy ignores a remediation key type the plugin fills in, and the disk encryption configuration ignores the empty recovery-key section Jamf Pro reports. An unknown ADE instance name makes the plugin retry for several minutes before failing.
- Live-verified on both test instances with a user account: connect and preflight, custom object deploy, drift restore and keep, adoption, snapshot, a rollout, Day 0 and hand-over. API-client (OAuth) sign-in is live-verified too: connect, deploy, check for changes and discovery.
- Taking a Jamf Pro API tenant out of the app by hand (`JAMFPRO_*` variables, `deploymenttheory/jamfpro`) is documented but not live-verified; Export as Terraform for such tenants is (the export UI suite of 1.1 with EXPORT_CONNECTION=jamfpro).
- Failed creates are looked up and adopted after a deploy for Jamf Pro API tenants too: policies, macOS configuration profiles and App Installer deployments (patch titles only on the Jamf Platform API). Unit-tested; not live-verified on a Jamf Pro API tenant.

## Team Mode caveats
- Git auth assumes the Mac has gh/SSH credentials configured; an in-app PAT flow is designed, not built.
- Engine state lives on the repository’s `jamf-deployer-state` branch through terraform-backend-git (bundled, run on demand on the loopback address); locks are the backend’s `locks/…` branches. Lock expiry is manual (Force Unlock); no auto-TTL.
- Join-time tenant ID conflicts are skipped, not merged.
- Repo access = access to all tenant records (plain JSON: names, baselines, scope IDs) and the encrypted engine state. Engine state is encrypted with one team passphrase (kept in each Mac’s Keychain); credentials are never in the repo — each engineer uses their own API client or account.
- Live-verified in 1.1 against a private test repository (Team Mode isn’t part of the 1.2 live UI tests: no test repository is configured; unit tests cover it): create (no state on main, encrypted state on the state branch), check and restore through the backend, a teammate’s lock reported and force-unlocked, leave (state back on the Mac), join with the passphrase, tenant removal clearing record and state, and Export as Terraform refusing a tenant a teammate has locked, then exporting it from the team space once unlocked.
- A tenant runs one engine operation at a time on a Mac (preview, check or deploy); a second request is refused with a message.
- The team passphrase is checked against the team space’s encrypted state before it’s accepted: creating a team space writes a small encrypted passphrase check to the state branch, and a team space without one gets it the next time the passphrase is confirmed. A wrong passphrase, or one that couldn’t be checked, is refused.
- Store syncs run one at a time. A pull that conflicts with this Mac’s changes is undone (this Mac’s commits are kept), and a store with an unfinished Git merge is never committed or synced. When the team sync fails, previews, checks and deploys don’t start until the store syncs.

## Taking a tenant out to plain OpenTofu
Live-verified: `tenants/<id>/generated/` + `state/` + the env vars (`JAMFPLATFORM_*`, `TF_ENCRYPTION` with the recovery-sheet passphrase) run under vanilla OpenTofu ≥ 1.13 with providers from the public registry once the copied lock file is removed (it records the bundled, re-signed provider checksums). After a one-time decrypt with OpenTofu, HashiCorp Terraform 1.16 plans the same state with “No changes”. From then on, the HCL is yours. Export as Terraform does the same in one step for any number of tenants (see below).

## Packaging and release
- Releases are signed and notarized (Developer ID, hardened runtime); the embed script signs the provider binaries inside the mirror archives at build time.
- Unit tests: about 170 in the app target (Jamf DeployerTests) and about 175 in JamfDeployerCore. Demo mode: 21 smoke UI tests in every release check (dashboard, checks, keep and restore, preflight, connect and remove, the baseline editor, block settings and pickers, Day 0, the catalog library, history, the Demo Mode marker, the guided tour, menus). Live UI tests (1.2, JTKit's live-check switch, jamf-test-a and jamf-test-b only, `JTKTEST` objects): every release check connects and removes a tenant, deploys a demo-catalog block with Preview and Apply, adopts an object, finds a change made in Jamf, restores and keeps it, removes everything, and captures from the production read role with a Preview on jamf-test-b and no apply. The full live suite (custom objects and catalog blocks on both connections, the Jamf Pro API flows, history, documentation, snapshot, clone and capture, a two-ring rollout, the Fleet preset conflict, Export as Terraform for review, a catalog release that renames a group, and the Mac App Store Apps block on a tenant with an Apps and Books location) runs on request. Before 1.2 the functional suites ran from separate scripts and also covered Team Mode and Export as Terraform end to end (export and move, the exported workflows, Destroy, hand-over); those push to a repository and are not part of the live tests.
- App Sandbox is off by design (child-process engine); Developer ID + notarization is the distribution model.

## Adopting an existing tenant
- Live-verified on a content-rich tenant: all 99 exporter types discovered (494 objects), 487 adopted with an import-only preview (no creates or deletes), deployed, converged to “No changes”, and a change made directly in Jamf was detected and restored.
- Adopt leaves out what the app can’t manage, with a note: objects whose secret values Jamf never exports (activation code, ADE server token, GSX credentials) and enrollment invitations. References from adopted objects to anything left out are pointed at the object’s existing Jamf ID, and values the export supplies are written into the adopted configuration.
- The exporter can leave PreStage sections out (device naming, purchasing, location, account settings, Setup Assistant skips). Adopt marks the missing ones as ignored, so the first deploy keeps the values in Jamf instead of clearing them; those sections aren’t drift-checked.
- Enrollment customizations capture with their text panes; the export downloads each icon so captured blocks upload their own copy (live-verified Demo → Sandbox, adopt import-only). LDAP panes are left out (they name the origin’s directory server); single sign-on panes are kept with a warning — untested live, no SSO-enabled test tenant.
- App Store apps (Mac and iPad/iPhone) license through the tenant’s Apps and Books location: the built-in blocks look the location up by name and each app by Adam ID (live-verified on the Sandbox); captured apps that used a location get the same lookup with an editable setting. A tenant without licenses for an app gets Jamf’s 409 translated into plain language.
- Mobile devices: profiles, apps, extension attributes, groups and PreStages adopt, capture and clone like their macOS counterparts (live-verified Sandbox → Demo, both capture modes). Blueprints capture and adopt as well (live-verified).
- Objects an adopted object references by Jamf Pro ID or name (for example a scope group) are adopted with it: only `.id` references can be pointed at an existing ID.
- **Adopt More…** lists only objects not yet adopted and adds them to the record; already adopted objects are left untouched.
- **Hand-over** is prepared, previewed and deployed like any change, and can be canceled until it deploys; the adopted configuration is archived next to the record once it has.

## Composition
- **Two blocks owning one tenant-wide setting** are refused when the workspace is generated, with a message naming both blocks.
- **Two new objects with one name aren’t caught in Preview**: Preview stops when a new object takes the name of one that already exists in Jamf (Jamf Platform API tenants), but not when two blocks would both create the same name. For example, selecting the demo catalog’s Categories block next to a captured categories block while “apply the tenant prefix to all names” is on can produce identically named categories (both create “<prefix>Enrollment”), and duplicated App Catalog titles (for example “TF - Google Chrome” next to “Google Chrome”) collide once rebinding collapses their deployments onto one target group. Jamf rejects the duplicates; deselect the duplicate objects at capture, or skip the prefix option. An editor-level collision warning is planned.
- **Removing a settings block only stops managing it**: Jamf has no “empty” state for tenant-wide settings, so the provider drops them from state and Jamf keeps the current values. The removal dialog says so.
- **Deploy history and drift mask sensitive values**: `tofu show -json` prints them in clear text; the copy kept in history (and the team repository) is redacted with the engine’s sensitivity markers, and Check for Changes shows sensitive fields as ••••••.

- **Deploys finish in order after an early delete**: when a catalog release renames an object another block uses, the engine can delete the old object before it updates its users, and Jamf refuses the delete. The app then finishes the deploy in order: first the approved changes that aren’t deletes, then the deletes, each from a fresh plan that must stay within the approved one. If Jamf changed in the meantime, the deploy reports the original error and asks for a new preview.

## Upstream dependencies being watched
- jamfplatform provider pinned at 1.7.2 (released 2026-10-28; a 124-object baseline converged to “No changes” on 1.6.0). Since 1.7.0 a Preview stops when a block would create an object whose name another object already has in Jamf, instead of Jamf refusing it during the deploy; packages upload straight to Jamf Cloud’s storage on Jamf Cloud tenants. OpenTofu is bundled at 1.13.9 (released 2026-11-05 with macOS downloads); OpenTofu never released 1.13.3 to 1.13.7 (its CHANGELOG marks them as skipped). Nothing between 1.13.2 and 1.13.9 changes the plan JSON or the streamed output the app reads; the recorded engine fixtures (1.13.1) still match. Blueprints’ top-level settings deprecated with a stated removal window (catalog already uses `component_blocks`). Settings › Advanced › Built-in tools flags newer upstream releases of OpenTofu, the three engine plugins, jamformer and terraform-backend-git (checked once a day).
- jamformer 0.6.1 (like 0.6.0) emits Terraform-style identity imports that fail under OpenTofu; the app normalizes them (worth reporting upstream). It also always runs a search phase, so a selection of only settings-style types fails with “No resources to query” — the app retries those exports with a small helper type and drops its files (worth reporting upstream).
- jamfplatform 1.5.0 returned an unknown `self_service.display_notifications` after creating macOS configuration profiles (“invalid result object after apply”). Captured blocks set the attribute explicitly, drop the vestigial `self_service` object from install-automatically profiles, and trim the trailing description whitespace Jamf discards — all three sidestep provider/server inconsistencies and stay in place on 1.7.2 (worth reporting upstream).
- Full-tenant clones are live-verified: a 468-object clone of a tenant (policies, profiles, groups, apps, App Installers, patch titles, blueprints, settings singletons) applies to an empty tenant and converges to “No changes”. PreStages clone too: their ADE instance reference becomes a name-based lookup with an editable block setting, and Recovery Lock is turned off when its password (never exported) is missing. Objects that can’t move — icons, invitations, built-in groups, default allowed file extensions, the cloud distribution point, Jamf Patch reporting attributes, compliance benchmarks, values Jamf doesn’t export, a login page without disclaimer text — are left out at capture with per-item warnings. All 24 settings-style types were exported one by one and in one bulk export (identical output); the 20 portable ones deploy alone and together with a 400-object baseline.
- Platform OAuth tokens live 900 s (handled); provider request pacing left at its real default (0 ms).
- Compliance benchmarks auto-create an audit policy in Jamf Pro (Jamf-managed; excluded from drift logic by the noise list).

## Scale honesty
Verified with a handful of tenants, a 440-object 31-block baseline and a 468-object full clone. Fleet views, drift batching (3 at a time) and the Git store should handle dozens of tenants comfortably; hundreds are untested.
